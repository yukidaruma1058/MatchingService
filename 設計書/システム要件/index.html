選定理由

Python + FastAPI（API / バッチ共通）

Gmail SDK・外部 AI API クライアントを Python から利用でき、メール取込・要約・マッチングを同一言語で実装できる。 FastAPI は型ヒント・自動 OpenAPI ドキュメント・非同期対応があり、小規模チームでも API 仕様の共有が容易。 バッチは常駐ワーカーではなくワンショット実行とし、画面・API・docker compose run からの手動起動のみとする。

Next.js（フロントエンド）

管理画面主体の CRUD・検索・詳細表示に適したフルスタック React フレームワーク。 TypeScript による型安全、App Router によるルーティング、本番向け standalone ビルドを Docker で配信。 API は FastAPI に分離し、フロントは BFF なしの直接呼び出し（NEXT_PUBLIC_API_URL）とする。

PostgreSQL

人材・案件・マッチ結果・送信履歴などリレーショナルなデータが中心。 JSONB（スキル配列・設定値）も使えるため、構造化データと柔軟な属性を両立できる。 全文検索拡張や集計クエリも将来追加しやすい。

Gmail API + 手動バッチ

受信トレイのラベル（SES人材紹介 / SES案件配信）で対象メールを絞り込み。 リアルタイム Push ではなく手動バッチ取込とすることで、再実行・冪等性の管理が容易。 OAuth トークン・credentials は secrets/ に配置し git 管理外とする。

AI 利用方針（Cursor API 初期検証 / OpenAI API 代替）

初期実装では Cursor API を使ってメール抽出・要約品質を検証する。結果が要件を満たさない場合は、 OpenAI API など別 LLM へ切り替えられるよう、AI 呼び出し部はプロバイダ差し替え可能な構成とする。 コスト抑制のため、LLM は主に Gmail ラベルで分けた案件/要員メールの構造化抽出に利用し、 マッチング本体は必須スキル一致率、尚可スキル一致率、単価差分、稼働開始日、勤務地/リモート条件、 業務領域キーワード、過去応募状況を用いたルールベーススコアを基本とする。

  • ① BAT-001 メール振り分けバッチを手動実行し、案件メール・要員メールを Gmail ラベルで分ける。
  • ② ①完了後に BAT-002 メール取込バッチを実行し、AI を用いて案件/要員ごとの専用 schema へ要約・JSON 出力する。
  • ③ ②完了後に BAT-006 過去データ削除を実行し、設定した保持日数を超えた取込データを DB から削除する（0 の場合はスキップ）。
  • ④ ③完了後に BAT-003 で全案件に対して要員ごとのルールスコアを採点する。
  • ⑤ 提案送信・返信同期・AI判定は画面から手動実行する。
  • 同じ案件×要員の組み合わせはキャッシュし、再評価によるトークン消費を抑える。

Docker Compose（手動バッチ）

db / api / web / batch を一括起動でき、開発環境の再現性が高い。 バッチは Ofelia 等の cron では起動せず、画面・API・docker compose run から手動実行する。 アプリコード（api/ batch/ web/）と Docker 定義（.docker/）を分離し、責務を明確化。

外部連携・認証情報

連携先認証主な用途

Cursor API / OpenAI API API キー（CURSOR_API_KEY / OPENAI_API_KEY） 人材/案件メールの抽出・要約、ルール上位候補に対する補助評価・理由生成
PostgreSQL 接続文字列（DATABASE_URL） 全永続データの読み書き

提案メール送信も Gmail API 経由（元メールへの返信）。送信履歴は outreach_messages（および案件側は outreach_message_talents）に保存。 件名・本文は企業ごとの DB テンプレートではなく、コード内の固定フォーマットで生成する（BAT-007 / BAT-009）。

検討したが採用しなかった案

  • 企業ごとの DB メールテンプレート（email_templates） 提案文面は BAT-007 / BAT-009 の固定フォーマットとし、企業別テンプレ編集 UI・テーブルは持たない。要員提案のみ送信前に本文編集可。
  • 常駐ワーカー（Celery / RQ 等） 常時キューは不要のため、ワンショット batch を画面・API から手動実行する方が運用・デバッグが単純。
  • Node.js バックエンド（Express / NestJS） AI・Gmail 連携のライブラリ成熟度で Python を優先。フロントのみ Node/Next.js と役割分担。
  • MySQL / SQLite JSONB・複雑な集計・将来の全文検索を見込み PostgreSQL を採用。
  • Gmail Push（Pub/Sub リアルタイム通知） インフラ設定が重く、SES メール取込は数分〜十数分遅延が許容されるためポーリングで十分。
  • 自前 LLM / ローカルモデル 要約・抽出品質と開発速度を優先し、当面は外部 LLM API（初期は Cursor API）を利用。
  • モノリシック構成（Next.js API Routes のみ） バッチと API のライフサイクルが異なるため、FastAPI と batch を分離。
