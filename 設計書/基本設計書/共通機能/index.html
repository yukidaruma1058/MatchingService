共通機能設計書

API・バッチで共通利用するログ出力機能の基本設計

バッチ設計書 エラーコード一覧
機能ID: COM-001 対象: api/ batch/ 出力: api=stdout / batch=log/batch.log 形式: JSON Lines 個人情報マスキング

1. 機能概要

ログ出力共通機能は、API・バッチ・外部連携処理から同一形式でログを出力するための共通部品である。 障害調査、バッチ再実行判断、外部API失敗の切り分け、ユーザー問い合わせ対応に必要な情報を残す。

項目内容
対象処理FastAPI のリクエスト処理、Gmail 振り分け/取込バッチ、AI 要約、ルールスコア採点、LLM 補助判定、Gmail 送信、DB 更新処理
出力先API は標準出力。バッチは log/batch.log（BATCH_LOG_PATH で変更可）。Docker / Ofelia / 将来のログ基盤が収集する前提。
形式1行1イベントの JSON Lines。改行を含む本文は出力しない。
共通キーtimestamp, level, service, function_id, module, method, operation, event, message, request_id, error_code, error_message（エラー時）
禁止事項メール本文、OAuth token、Cursor/OpenAI API key、DB パスワード、個人情報の詳細をそのまま出力しない。

2. ログレベル

レベル用途出力例
DEBUG開発時のみの詳細情報。本番では原則無効。SQL生成前の条件、外部APIリクエストのメタ情報
INFO正常な処理開始・終了・主要な状態遷移。API受信、バッチ開始/終了、メール取込件数
WARN処理継続は可能だが確認が必要な事象。一部メールの要約失敗、対象データなし、リトライ発生
ERROR処理失敗、外部連携失敗、DB更新失敗。ERR-xxxx とともに出力
CRITICALサービス継続不能な異常。DB接続不可、必須設定不足、Gmail認証全件不可

3. 共通ログ項目

キー必須説明例
timestamp必須ログ出力日時。ISO 8601 UTC。2026-07-09T15:00:00Z
level必須ログレベル。INFO
service必須出力元サービス。api, batch
function_id必須業務機能ID。画面ID、API機能ID、バッチID、共通機能IDのいずれか。BAT-001, SCR-015, COM-001
module必須Python モジュールまたは処理コンポーネント。batch.gmail_ingest
method必須関数名・メソッド名・APIハンドラ名。fetch_message_body
operation必須業務操作名。メソッド名より利用者・運用者が理解しやすい粒度。Gmail本文取得
event必須イベント名。ドット区切り。gmail_ingest.started
message必須人が読める概要。Gmail ingest started
request_idAPI必須APIリクエスト単位の相関ID。req_...
job_idバッチ必須バッチ実行単位の相関ID。job_20260709_150000
error_codeエラー時必須エラーコード一覧 のコード。ERR-0021
error_messageエラー時必須利用者向け日本語メッセージ。error_messages.py の文言を基本とする。Gmail メールの取得に失敗しました。
entity任意対象テーブルまたは業務エンティティ。emails, talents
entity_id任意対象レコードID。存在する場合のみ。12345
gmail_message_id任意GmailメッセージID。本文は出さない。18f...
duration_ms任意処理時間ミリ秒。1280
extra任意追加情報。個人情報・秘密情報を含めない。{"count": 10}

6. マスキング方針

対象出力方針例
メール本文出力禁止。必要な場合は本文長やハッシュのみ。body_length=1200
メールアドレス原則マスク。ドメイン確認が必要な場合のみドメインを残す。t***@example.com
OAuth token / API key出力禁止。[masked]
DB接続文字列ユーザー名・パスワードを除外。postgresql://***@db:5432/matching
氏名・会社担当者名通常ログには出力しない。業務上必要な場合は DB ID を利用。contact_id=123

7. API / バッチでの利用方法

API

  • リクエスト受信時に request_id を生成し、レスポンスヘッダーと全ログに付与する。
  • API ハンドラごとに function_id、module、method、operation を設定する。
  • 例外ハンドラで error_code と HTTP ステータスを決定し、同じ情報をログとレスポンスに出力する。
  • 正常終了時は api.request.finished に status_code と duration_ms を出力する。

バッチ

  • 起動時に job_id を生成し、バッチ内の全ログに付与する。
  • バッチ全体は function_id に BAT-001 などのバッチIDを設定し、各処理関数で module と method を更新する。
  • メール単位の処理では gmail_message_id を付与し、再実行時の追跡を容易にする。
  • 一部失敗は WARN または ERROR として記録し、全体継続可否を バッチ設計書 の方針に従って判定する。

8. 実装方針

項目方針
配置API: api/app/（将来 common/logging.py）。バッチ: batch/app/logging_util.py, batch/app/error_messages.py。将来 shared/ 化を検討する。
初期化アプリ起動時・バッチ起動時にログレベル、JSON formatter、マスキング filter を設定する。
呼び出しlogger.info(function_id=..., module=..., method=..., operation=..., event=..., message=..., extra=...) 相当のラッパーを利用し、直接 print は使わない。
エラー連携エラーコード一覧 の ERR-xxxx を必ず含める。
テストマスキング対象がログに含まれないこと、必須キーが出力されることを単体テストで確認する。
