3. バッチ処理フロー設計

バッチはワンショット実行とする。起動は画面・API・``docker compose run`` による手動実行のみ（Ofelia 等の定期スケジューラは用いない）。 パイプラインは ① BAT-001 → ② BAT-002 → ③ BAT-006 → ④ BAT-003 → ⑤ BAT-008。 要員提案（BAT-007）・AI判定（BAT-004）・案件側提案（BAT-009）は画面手動。返信同期（BAT-008）はパイプライン末尾でも実行し、案件一覧／メール取込から単独実行も可能。 同一 Gmail メッセージの重複登録を避けるため、emails.gmail_message_id を一意キーとして冪等に処理する。

① BAT-001 メール振り分け 手動実行。gmail_sort_source_label 付きメールを取得し、件名を優先して検索ワードと照合して要員/案件ラベルへ振り分ける。件名だけで判定できない場合のみ本文先頭（既定 500 文字）も参照する。判別不能時は gmail_sort_unknown_label を付与する。既に振り分け後ラベル（要員/案件/判別不可/取込済み）付きのメールは再振り分けしない。
② BAT-002 メール取込・AI要約 ①完了後に実行。案件/要員ラベル付きメールを取得し、AI を用いてラベル種別ごとの JSON schema に抽出・要約する。必須項目不足時は要確認ステータスで保存する。
③ BAT-006 過去データ削除 ②完了後に実行。ingest_data_retention_days 設定に基づき、emails.created_at が保持日数より古い取込データを物理削除する。0 の場合はスキップ。Gmail 側は変更しない。削除後に BAT-003 へ進み、マッチング対象件数を抑制する。
④ BAT-003 ルールスコア採点 ③完了後に実行。全案件に対して要員ごとのルールスコアを算出し、match_runs / matches に保存する。
⑤ BAT-008 返信同期・OK/NG ④完了後にパイプラインでも実行。送信済み提案（talent_proposal / project_proposal）スレッドの返信を取得し設定ラベルを付与、AI（失敗時はキーワード）で OK/NG を判定。案件一覧／メール取込から単独実行も可。
⑥ BAT-007 要員への案件提案（手動） 画面から選択したマッチを人材紹介メールへ返信送信する。本文は talent_proposal_body / BAT-007 内の固定フォーマット（プレビュー時は本文編集可）。
⑦ BAT-004 AI判定（手動） 画面の AI判定ボタン。NG のルールスコアを 0 にし、OK かつ上位 N 人（案件ごと）に LLM 判定。詳細画面から選択したマッチも対象可。
⑧ BAT-009 案件への要員提案（手動） 同一案件の選択要員をまとめて、案件配信メールへ 1 通の返信で提案する。本文は BAT-009 の _build_body 固定フォーマット（画面での本文編集なし）。

5. BAT-001 メール振り分け

設定画面の Gmail 振り分け設定に基づき、ソースラベル付きメールを要員/案件/判別不可ラベルへ振り分ける。 判定ロジックは batch/BAT-001/classifier.py に実装する。

項目内容
バッチIDBAT-001
ジョブ名sort
実装batch/BAT-001/gmail_sort.py, batch/BAT-001/classifier.py
手動 APIPOST /api/batches/gmail-pipeline（ダッシュボード／メール取込）。CLI sort でも単独実行可
本文参照長SORT_BODY_PREVIEW_CHARS（既定 500）。件名だけで判定できない場合のみ本文先頭を使用

キーワード判定（件名優先）

  1. 件名のみを gmail_sort_keywords_talent / gmail_sort_keywords_project と照合する（大文字小文字は区別しない）。
  2. 件名で要員キーワードのみヒット → gmail_sort_label_talent を付与。
  3. 件名で案件キーワードのみヒット → gmail_sort_label_project を付与。
  4. 件名で両方ヒット、またはどちらもヒットしない → 件名 + 本文先頭（最大 sort_body_preview_chars 文字）を結合したテキストで同じルールを再判定する。
  5. 再判定でも一意に決まらない → gmail_sort_unknown_label（判別不可）を付与。

件名に「人材」等が明示されている一方、本文冒頭に営業定型文（「案件・人材・他商材のご紹介をお願いします」等）があり両方ヒットするケースでは、 件名優先により要員/案件のいずれかへ振り分けられる。

処理フロー

  1. バッチ開始ログ（gmail_sort.started）を log/batch.log へ出力する。
  2. system_settings から振り分けラベル・検索ワードを読み込む（gmail_sort.settings_loaded）。
  3. Gmail OAuth で接続し、ソースラベルおよび振り分け先・取込済みラベルの存在を検証する。不足時は ERR-0020 で開始前に異常終了する。
  4. ソースラベル付きメール ID を列挙し、1 件ずつ本文を取得する。
  5. 要員/案件/判別不可/取込済みラベルのいずれかが既に付いているメールはスキップする。
  6. 件名優先のキーワード判定を行い、判定ラベルを付与してソースラベルを除去する（gmail_sort.message_sorted）。
  7. 振り分け結果を emails テーブルへ upsert する。
  8. 走査件数・振り分け件数・スキップ件数・失敗件数を含む完了ログ（gmail_sort.finished）を出力する。

エラー・継続方針

  • 認証失敗・必須ラベル不足など全件継続不能な事象はバッチ全体を異常終了する（batch.job.failed）。
  • 個別メールの取得・ラベル更新失敗は gmail_sort.message_failed として記録し、他メールの処理は継続する。
  • ERROR ログには error_code と利用者向け error_message の両方を含める。API 手動実行時は直近 ERROR を画面へ返す。

6. BAT-002 メール取込・AI要約

振り分け後の要員/案件ラベル付きメールを取得し、AI で JSON 抽出し talents / projects へ保存する。 実装は batch/BAT-002/。

項目内容
バッチIDBAT-002
ジョブ名ingest
実装batch/BAT-002/gmail_ingest.py, batch/BAT-002/summarizer.py
手動 APIPOST /api/batches/gmail-pipeline（ダッシュボード／メール取込）。CLI ingest でも単独実行可
参照 APIGET /api/emails, GET /api/talents, GET /api/projects, GET /api/dashboard

AI プロバイダ優先順

  1. CURSOR_API_KEY あり → Cursor SDK（cursor-sdk）で JSON 抽出
  2. なければ OPENAI_API_KEY → OpenAI Chat Completions（JSON mode）
  3. どちらも無い → 件名 + 本文先頭のヒューリスティック（常に needs_review）

処理フロー

  1. 開始ログ（gmail_ingest.started）を log/batch.log へ出力する。
  2. 人材/案件/処理済みラベルの存在を検証する（不足時 ERR-0020）。
  3. 人材ラベル・案件ラベル付きメールを列挙し、処理済み付きはスキップする。
  4. AI 抽出結果を正規化し、emails を upsert したうえで talents または projects を email_id UNIQUE で upsert する。
  5. 必須欠落時は emails.status=needs_review、完全失敗時は failed（Gmail は処理済みへ移さない）。成功時は処理済みラベルへ付け替え。
  6. 完了ログ（gmail_ingest.finished）を出力する。

6.5 BAT-003 ルールスコア採点

全 active 人材 × open 案件をルールベースで採点し、match_runs / matches に保存する。 実装は batch/BAT-003/。足切りは行わない。案件一覧のスコア帯はこのルールスコアを正とする。

項目内容
バッチIDBAT-003
ジョブ名match
実装batch/BAT-003/match_score.py, scorer.py, google_routes.py, commute.py
手動 APIPOST /api/match-runs
参照 APIGET /api/match-runs, GET /api/match-runs/{id}/matches

配点（合計 100）

観点配点内容
スキル一致40必須スキルカバー率。必須空→中立20、人材スキル空→0
単価適合25希望単価 vs rate_min/max
稼働時期15available_from vs start_date
勤務形態10work_style のみ（地名一致はしない）
通勤時間10Google Routes TRANSIT。未取得・欠損→中立5。フルリモート→10（API なし）

二パス採点

  1. Pass1: 全組合せを採点。通勤は中立 5（API 呼び出しなし）。
  2. Pass2: 案件ごとに Pass1 上位 ai_judgement_top_n（既定5）人だけ Google Routes で通勤分を確定しスコアを更新。
  3. 駅ペアは commute_cache に保存し再利用する。
  4. 月次カウンタ commute_api_usage: 8,000 で警告、10,000 で Pass2 の API 呼び出し停止（アプリ側制御）。

Google Routes 設定

  1. Google Cloud で Billing を有効化し、Routes API を有効化する。
  2. API キーを作成し Routes API に制限する。
  3. .env に GOOGLE_MAPS_API_KEY を設定する（未設定時は通勤中立のまま）。
  4. 無料枠は Compute Routes Essentials 月 10,000 回。compose の environment で空文字上書きしないこと。

処理フロー

  1. 開始ログ（matching.rule_score.started）。
  2. 人材または案件が 0 件なら ERR-0026 で停止。
  3. match_runs を作成し Pass1/Pass2 を実行、matches を保存。
  4. 完了ログ（matching.rule_score.finished）。

7. BAT-006 過去データ削除

設定画面で指定した保持日数（ingest_data_retention_days）を超えた取込データを PostgreSQL から削除する。 Gmail 上のメールやラベルは変更せず、本システム DB に登録された取込データのみを対象とする。 取込パイプラインでは BAT-002 完了後に実行し、古いデータを掃除したうえで BAT-003 へ進める。

項目内容
バッチIDBAT-006
ジョブ名cleanup
実装batch/BAT-006/
手動 APIPOST /api/batches/ingest-cleanup / パイプライン内（BAT-002 の後）
設定system_settings.ingest_data_retention_days（0 = 削除しない）
判定基準日emails.created_at（DB 登録日時）
連動削除talents / projects は email_id の ON DELETE CASCADE

処理フロー

  1. バッチ開始ログ（ingest_cleanup.started）を出力する。
  2. system_settings から ingest_data_retention_days を読み込む。未設定時は環境変数 INGEST_DATA_RETENTION_DAYS、それも無ければ 0 とする。
  3. 保持日数が 0 以下の場合、削除せず ingest_cleanup.skipped を出力して正常終了する。
  4. 削除基準日時 cutoff = now() - retention_days を算出する。
  5. emails.created_at < cutoff に該当するレコードを物理削除する。
  6. （将来）talents / projects で取込元 email_id が削除対象に紐づくレコードを削除する。
  7. （将来）孤立した matches 等の関連データを整理する。初版では emails のみ。
  8. 削除件数・保持日数・処理時間を含む完了ログ（ingest_cleanup.finished）を出力する。

削除対象と DB 方針

フェーズ対象テーブル条件備考
初版 emails created_at < cutoff 振り分け・取込の元データ。Gmail 側は触らない。
将来拡張 talents, projects 紐づく email_id のメールが削除対象 BAT-002 実装完了後に連動削除を追加。
対象外 companies, contacts, applications, outreach_messages — マスタ・応募・送信履歴は保持期間削除の対象外。
  • 削除は物理削除（DELETE）とする。1 トランザクションで完結し、途中失敗時はロールバックする。
  • 削除件数 0 件でも正常終了とする。DB エラー時のみ異常終了（ERR-0030 等）。
  • 設定値が範囲外の場合は ERR-0017 としてバッチ開始前に停止する。
  • ログの function_id は BAT-006、module は BAT-006.cleanup とする。

8. 外部連携設計

Gmail API

  • 認証は OAuth 2.0。secrets/credentials.json と secrets/token.json を Docker volume で /secrets に読み取り専用マウントする。
  • 連携中アカウントは Gmail profile API で取得し、設定画面に読み取り専用で表示する。
  • 取込対象は gmail_sort_label_talent / gmail_sort_label_project のラベル付きメール。
  • 送信は Gmail API の send を利用し、送信成功後に Gmail メッセージ ID を保存する。

AI API（Cursor API / OpenAI API）

  • 初期検証は CURSOR_API_KEY と Cursor API を使用する。結果が要件を満たさない場合は OpenAI API など別プロバイダへ切り替える。
  • 要約出力は JSON schema 相当の構造を期待し、パース失敗時はメール処理状態をエラーとして保持する。
  • マッチング本体はルールベースで行う。LLM 補助判定はルールスコア採点の後続処理として、案件ごとのルールスコア上位 ai_judgement_top_n 件だけに限定する。
  • 同じ案件×要員の AI 判定結果が存在する場合はキャッシュを利用し、AI API 呼び出しを抑制する。

バッチ起動同一バッチ実行中、依存サービス稼働、開始条件ERR-0027 / ERR-0028多重起動はスキップ、それ以外は異常終了

11. エラー処理・ログ

  • API は {"error_code":"ERR-xxxx","error_message":"..."} 形式でエラーを返す（バッチ手動実行 API は log/batch.log の直近 ERROR 行を参照）。
  • API はバリデーションエラーを 400、未存在を 404、競合を 409、外部連携失敗を 502、想定外を 500 として返す。
  • バッチはメール単位で失敗を分離し、1件の失敗で全体を停止しない。認証エラーなど全件継続不能な場合のみ異常終了する。
  • バッチログは ログ出力共通機能 に従い log/batch.log へ JSON Lines 形式で出力する（環境変数 BATCH_LOG_PATH で変更可）。画面にはログ本文を表示せず、エラーコードとメッセージのみ表示する。メール本文や OAuth token は出力しない。
  • 障害箇所を特定できるよう、全ログに function_id、module、method、operation を含める。
  • 再実行可能性を優先し、エラーコード、Gmail ID、DB ID、処理ステータスをログに含める。
